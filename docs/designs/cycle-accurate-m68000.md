# Design: Cycle-Accurate Motorola 68000

> **Status: proposed, 2026-09-08.** Written to answer one question: is
> converting the M68000 from instruction-level to per-cycle worth doing, and if
> so, how. The recommendation is **yes, with a stop-and-measure gate after M1**,
> for the reasons under [Recommendation](#recommendation).
>
> The sibling effort is finished:
> [`cycle-accurate-i8088.md`](cycle-accurate-i8088.md) converted the I8088 and
> records what its plan got wrong. This document is written to inherit those
> corrections rather than repeat them, and says where it does.
>
> The existing [`m68000-emulator.md`](m68000-emulator.md) describes this core as
> built. It is not restated here.

## The premise the issue was written on is wrong, and that changes the design

`phosphor-emulator-cycle-accurate-m68000-5y6e` says that per-cycle work "needs a
bus-trace oracle it does not provide", of SingleStepTests/680x0. That was true of
our harness and false of the suite. `cpu-validation/src/lib.rs` carries the
comment `transactions (per-cycle bus trace) is present but unused`, and `length`
is deserialized with the note "not compared yet: the harness is state-only".

This is the same discovery the I8088 conversion turned on, in the same place:
a recorded per-cycle field, on disk, that the harness had been throwing away.

## The oracle

The set we already have on disk is `SingleStepTests/680x0` (the submodule at
`cpu-validation/test_data/680x0`, per `.git/config`). Each of its 1,000,060
vectors carries three things beyond the register state we already compare.

- **`length`** is the instruction's total clock count.
- **`transactions`** is the ordered list of bus cycles. Two forms, per the
  suite's own README:
  - `["n", 122]`, the bus idle for 122 clocks.
  - `["r", 4, 6, 3076, ".w", 10786]`: kind (`r` read, `w` write, `t` the TAS
    indivisible read-modify-write), length in clocks, the posted function code
    (FC2..FC0), the posted address, the access size, and the value on the data
    bus.
- **`prefetch`**, in both `initial` and `final`, is the literal two-word
  prefetch queue.

**The transactions tile the instruction exactly.** `NOP` is `length` 4 with one
4-clock read; `LSL.l D1, D6` is `length` 126 with a 4-clock read and `["n", 122]`.
So this is not a summary of which accesses happened. It is a complete per-clock
timeline in run-length form, and the position of every bus cycle within the
instruction is fully determined by it. That is the resolution the whole design
needs, and it is what makes the ladder in [Decision 3](#decision-3-validation)
possible.

Two further points that constrain the implementation:

- **The queue invariant is checkable at every instruction boundary.** Read the
  `NOP` vector: `initial.pc` 3072 with `prefetch` `[20081, 10835]`, `final.pc`
  3074 with `prefetch` `[10835, 1657]`, and the one transaction is a read of
  address 3076 returning 1657. So `prefetch[0]` is the word at `pc` and
  `prefetch[1]` is the word at `pc + 2`, before and after. The queue is exactly
  two words ahead of the consumption pointer, and 1,000,060 vectors assert it.
- **A byte access is one half-word transaction.** The README states that for
  byte accesses "you can infer UDS or LDS by inspecting the lowest bit of the
  posted address" and that the recorded value "is that from whichever half of
  the bus was active". Decision 4 below is why that settles a currently open
  bug.

### There are two independent vector sets, and that is the strongest fact here

**Neither is recorded from hardware, and they were generated by different
implementations.** The I8088 suite was captured off a real part with a hardware
harness. Nothing equivalent exists for the 68000. What exists instead is two
separate repositories in the same organization, which are not two names for one
thing:

- **`SingleStepTests/680x0`**, what our submodule points at. Its README states
  the methodology: generated from an implementation that "conforms to all
  available documentation, official and third-party", "passes all other
  published test sets", and "has been verified by usage in an emulated machine".
  That is a documentation-derived implementation, verified by use.
- **`SingleStepTests/m68000`**, added as a second submodule at
  `cpu-validation/test_data/m68000`. Its README states it is "generated from
  MAME's microcoded emulator". That generator is the microcode-level model
  described above, built from the part's die-extracted microcode ROM, nanocode
  ROM and decode PLA, and it has been the mainline 68000 implementation there
  since 2023 rather than a side experiment. Its provenance therefore runs back
  to the silicon rather than to the manuals.

**They are kept side by side rather than one replacing the other.** Replacing
was considered and rejected: `680x0` is the corpus the state gate is green on,
and `m68000` disqualifies itself on two instructions that `680x0` covers
(below).

**`m68000` is a strict coverage superset**, 127 vector files against 124, and
the three it adds are `ILLEGAL_LINEA`, `ILLEGAL_LINEF` and `STOP`. This core
implements all three and has never had a vector for any of them.

**Its differences are in our favor on exactly the points this conversion turns
on**, and each of these was checked against decoded data rather than taken from
the README.

- **The posted address is the true word address, with UDS and LDS carried as
  separate signals.** The part has no A0 pin, so this is what the bus actually
  shows. `680x0` instead posts the unaligned byte address and leaves the strobe
  to be inferred from bit 0. A decoded `MOVE.b (d8, A7, Xn), (A5)+` reads
  `["r", 4, 1, 4272488, ".b", 45824, 1, 0]` and writes
  `["w", 4, 1, 12788194, ".b", 179, 0, 1]`: both addresses even, the strobes
  saying which half. This is the more faithful representation and it is
  precisely what
  [Decision 4](#decision-4-byte-strobes-are-not-a-separate-project) needs.
- **Byte data is bus-positioned.** The same byte `0xB3` appears as `45824`
  (`0xB300`) under UDS and `179` (`0x00B3`) under LDS, where `680x0` normalizes
  every byte to 0..255. Comparison must normalize by strobe, and a harness that
  forgets to will fail every odd-address byte access for the wrong reason.
- **It adds the `re` and `we` cycle kinds** for read and write address errors.
  Its README explains why they are there rather than omitted: on the real part
  those cycles still happen, AS simply is not asserted, so the result is not
  committed. This core already models the address-error abort exactly at state
  level and will have to place those cycles in time.

**And its caveats are stated, which is worth as much.** Its README says "all of
the tests except TAS and TRAPV are verified as good"; that `TAS` "doesn't
properly handle the special 5-cycle TAS read-modify-write timing"; that the
`TRAPV` tests behave oddly with respect to the S bit; and, plainly, that any bug
in its generator is reflected in the tests. It also says the format "may not be
the final form", so **pin the submodule and do not float it.**

**`pc` is not the execution point in this set, and that is the one trap.** Its
README says PC comes from the generator's `m_au`, the "next prefetch address",
"+4 from where the test starts executing". Decoded `NOP` confirms it exactly:
`initial.pc` 911852, `initial.prefetch` `[20081, 55472]`, RAM holding `0x4E`
`0x71` at 911848 and 911849, which is `0x4E71`, which is 20081. So execution
begins at `pc - 4`, `prefetch[0]` is the word at `pc - 4`, `prefetch[1]` the
word at `pc - 2`, and the fetch during the instruction reads `pc` itself. The
`680x0` set puts `pc` at the execution point instead. Reconcile, do not compare
across sets naively.

**One more population difference.** `680x0` starts 99% of its vectors in
supervisor mode and posts function codes 6 and 5. The `m68000` set is not
skewed that way: the first `NOP` runs in user mode with function codes 2 and 1.
Good for coverage, and a reason the two sets' population splits will not line
up.

**Ingesting it costs a decoder, and the decoder is small.** 145 lines of Python
in the repo, and the container is simple: a `0x1A3F5D71` header and a test
count, then per-test magics framing a name, two states of nineteen
little-endian registers plus two prefetch words and a RAM list, and a
transaction list. Decoded, it yields the same top-level shape this harness
already deserializes: `name`, `initial`, `final`, `length`, `transactions`.
**Note that the 16-bit RAM the README mentions is the container's encoding, not
the decoded form**: the decoder splits each word back into two `[address, byte]`
pairs, so `M68000Regs.ram` needs no change. **The transaction record is a
superset of the one we already read**, adding UDS and LDS after the data word
and the two extra kinds. So the harness work is a decoder and a widened record,
not a second harness.

**`length` tiles here too, measured over the whole corpus.** Decoding all 127
files gives 317,500 cases, and **every one of them tiles**: no case's
transactions sum to anything but its recorded `length`, and none reports zero
clocks. `length` is stored in the container rather than derived from the trace,
so the two could have disagreed and do not. The corpus is smaller than
`680x0`'s, 2,500 cases per file against roughly 8,000, so it trades depth per
instruction for the wider instruction coverage above.

**And the `TAS` caveat is worse than the README implies.** Across all 317,500
cases the kind histogram is 832,245 reads, 562,558 writes, 333,171 idle spans,
53,160 read address errors and 2,446 write address errors. **There is not one
`t` entry in the corpus.** The set does not merely get the indivisible
read-modify-write timing wrong, it never emits the cycle kind at all, so
`680x0` is the only source for what `TAS` does on the bus. That is a concrete
instance of the rule above: on this one instruction the stronger-provenance set
is not an authority at all.

**The discipline this buys, and it is the reason to take both.** A single
generated oracle has the failure mode this project keeps writing down: the
subject and the standard risk coming from the same place, and nothing can tell a
correct implementation from one that agrees with its source's mistakes. Two
independently generated traces make the standard falsifiable.

- Where the two sets agree and this core differs, **this core is wrong.** No
  argument, no fitted constant.
- Where the two sets disagree, **that is a finding, not a nuisance.** It is
  resolved by reading the microcode, and the answer goes upstream as a bug
  report against whichever set is wrong.
- A disagreement with one set alone is never on its own grounds to change a
  constant here.

**What does not change.** `680x0` stays as the state gate, exactly as it is and
green at 1,000,058 of 1,000,060. It is the regression net, it has been correct
in places where the manuals are silent and other emulators disagree, and
swapping the gate's corpus mid-conversion would throw away the one check that
does not move.

### What was considered and set aside

- **`m68k-rs`** (github.com/benletchford/m68k-rs) was considered as a
  steppable reference and set aside for two reasons, the second of which is the
  real one. Its `step()` executes one whole instruction and returns the cycles
  it took, so there is no representable state mid-instruction and nothing to
  advance one clock at a time. And it is validated against *these same
  fixtures*: its README reports 261,894 cases matching their fixture cycle and
  bus-access **totals**, with access sequence and per-access timing left to
  separate audit tools that are ignored rather than gating. So it sits
  downstream of the oracle we already have, checked at the two rungs below the
  ones this conversion needs. Taking it as the standard would make the subject
  and the standard come from the same place, one resolution coarser than the
  source. It does model a two-word prefetch queue and access ordering for both
  the 68000 and the 68010, which makes it worth reading as a second opinion
  where no fixtures exist at all
  (Decision 6). A second opinion is a hypothesis generator, not an oracle.
- **A microcode-level reference for the 68000 exists locally** and is the
  closest thing to the published microcode the I8088 conversion transcribed:
  the 68000's own microcode ROM, nanocode ROM and decode PLA, die-extracted and
  published as decode tables, at
  `/home/pjl/ws/mame/src/devices/cpu/m68000/m68000gen.py`. It is the source to
  read when the vectors show a sequence this core cannot explain, exactly as the
  I8088's timing rows came from transcribed microcode rather than from a table.
  It covers the 68000 and 68008 only.

## What the core does today

`core/src/cpu/m68000/README.md` states the gap under "Execution model: atomic,
not per-cycle": an instruction decodes and applies its full effect on its first
cycle, then burns the remaining documented cycles as bus-idle waits through
`ExecState::Execute(n)`.

**Unlike the I8088, that description is accurate.** The I8088's `Execute(_)` arm
turned out never to be constructed, so that core had no instruction timing at
all and ran roughly an order of magnitude fast. This core has 115 `finish()`
call sites and genuinely burns its documented cycles. The consequence matters
for [Performance](#performance): there is no free lunch waiting here.

What is wrong is therefore narrower and more specific than it was for the I8088:

- **There is no prefetch queue.** The two-word queue is what makes the
  documented cycle counts come out, and it is directly recorded in the oracle.
- **Bus ordering within an instruction is an artifact of the interpreter.** The
  operand accesses happen in whatever order `execute.rs`-equivalent code makes
  them, all on one clock, and then time is charged afterwards.
- **The one place this already hurts is shipped.** `M68000::prefetch_pc` exists
  because Road Runner's Slapstic snoops the address bus and the game arms it by
  *prefetching* an instruction at a magic address. The core carries a hand-rolled
  one-word-ahead prefetch tracker, resynced on every non-sequential PC change,
  purely so that one board sees fetches in hardware order. That is a real
  prefetch model with one user, built because the atomic model could not express
  the thing the hardware does. A real queue subsumes it.
- **Bus phase is video phase on three of the four boards.** Food Fight runs the
  68000 at 6.048 MHz, which is also the pixel clock, so CPU cycles map 1:1 to
  pixel clocks; Atari System 1 does the same at 7.15909 MHz. Anything that wants
  video timing derived from bus phase is one step away on those boards and
  unreachable today.

What is good and should survive: `addressing.rs` already resolves every EA into
one `Ea` enum that read, write and read-modify-write share, the flag cores in
`alu.rs` are pure, and the suite passes 1,000,058 of 1,000,060 vectors. None of
that is about timing, so all of it carries over.

## Architecture facts (reference points)

- **Bus cycle**: eight clock states S0 through S7, which is four clock cycles at
  the CPU clock, plus wait states inserted between S4 and S5 when DTACK is late.
  All the suite's counts assume immediate DTACK.
- **Data bus is 16 bits.** A word access is one bus cycle; a long is two. A byte
  access is one bus cycle with a single strobe, UDS for the even byte and LDS for
  the odd one.
- **Prefetch queue is two words.** The instruction word being decoded and one
  word ahead. A taken branch, a jump, a return or an exception flushes and
  refills it.
- **Function codes FC2..FC0** classify each bus cycle as user or supervisor and
  program or data. The vectors post 6 for supervisor program and 5 for
  supervisor data, and 99% of vectors start in supervisor mode.
- **Address error**: a word or long access at an odd address aborts the
  instruction at the faulting access and vectors through 3. This core already
  models it exactly, including the per-instruction microcode quirks.

## Decision 1: one `tick()` is one clock cycle

Rejected alternative: one `tick()` = one bus cycle. Three reasons against, and
the third is decisive.

- The bus cycle is not a fixed length once wait states exist.
- The idle records in the oracle (`["n", 122]`) are in clocks, not bus cycles,
  and 122 is not a multiple of 4.
- **The boards already call us once per clock.** `foodf.rs:670` is
  `cpu.execute_cycle(board, BusMaster::Cpu(0))` inside a per-cycle loop, and the
  clock tree declares the CPU domain at 6.048 MHz (Food Fight, Quantum) and
  7.15909 MHz (Atari System 1). A clock *is* one CPU cycle. So this needs no
  board change and no clock-tree change: the existing call site keeps its
  meaning and only the meaning of what happens inside changes.

This is the same answer the I8088 reached, for the same reason, and it lands in
the easier place here: the I8088's T-state and the 68000's clock are both
already the unit the board counts in.

## Decision 2: model the prefetch queue

Model it. Without it there is no point doing the conversion: the queue is what
turns documented best-case timings into what the part does, it is directly
recorded in the oracle in both `prefetch` arrays, and the core already carries a
degenerate one-word version of it for the Slapstic.

Shape:

- Two words, matching the recorded invariant: `queue[0]` is the word at `pc` and
  `queue[1]` the word at `pc + 2`.
- Refill runs as its own small state machine issuing program-space bus cycles
  (FC 6 in supervisor mode) when there is room and the execution unit is not
  using the bus.
- Every control transfer flushes and refills. The I8088 conversion's clearest
  finding applies here without change: **detecting a control transfer by
  comparing addresses does not work**, because a taken branch with a zero
  displacement lands where execution would have gone anyway and the part still
  flushes. Every transfer must say so explicitly through the code that sets PC,
  not through a proxy for it.
- `prefetch_pc` and its resync are deleted, and the Slapstic gets its fetch order
  from the queue instead. That is a behavior change on a shipped board and it
  gets the golden frame treatment: named mechanism, look at the image.

## Decision 3: validation

**Keep the existing state gate exactly as it is.** 1,000,058 of 1,000,060 across
124 files, the two skips being known-bad ASL.b vectors whose expected state is
unrelated to the executed instruction. That gate is the regression net that keeps
the conversion honest instruction by instruction; a rewrite that breaks it has
broken the CPU no matter how good its bus trace looks.

Add a per-cycle gate beside it that replays `transactions`. Widen it in this
order, and **each rung must be able to fail on its own**:

1. **`length` only.** Our total clock count against the vector's. Needs no bus
   modeling to be meaningful and catches gross timing errors at once.
2. **Transaction sequence, kinds and order only.** Read/write/TAS in the right
   order, durations ignored. Proves the operand pipeline runs its accesses where
   the part does.
3. **Positions.** Durations and the idle gaps, so every transaction starts on
   the clock the recording starts it on. This is the rung that separates a
   correct sequence from a correct-looking one, and it is where the I8088's
   equivalent found that two errors had been canceling.
4. **Address, size and data per transaction.**
5. **Function code.** Program against data, user against supervisor.
6. **`final.prefetch` equality**, plus the standing invariant that `prefetch[0]`
   is the word at `pc`.

Rungs 1 and 2 can be built and reported *before* any conversion work, against
today's atomic core, and that is M1. The number they produce is the evidence the
"then decide" in the issue asks for.

**Run the ladder against both vector sets**, for the reason under
[There are two independent vector sets](#there-are-two-independent-vector-sets-and-that-is-the-strongest-fact-here).
What it buys is that the standard becomes falsifiable rather than
self-confirming.

**Correction, from building it: a per-case cross-set diff is impossible.** The
first draft of this section called for "a third figure for the cases where the
two sets disagree with each other". There are no such cases. The two suites were
generated separately from different random states and share no vector: `680x0`
opens `NOP` with `pc` 3072 and the name `4e71 [NOP] 1`, `m68000` with `pc`
911852 and the name `000 NOP 4e71`. Nothing in one has a counterpart in the
other.

What is comparable is **our agreement rate per instruction file, set beside set**.
Where our rate against one suite differs materially from our rate against the
other for the same instruction, the two oracles are saying different things
about it. That is the cross-set signal, at the only resolution the corpora
allow, and the gate reports the rows that differ by five points or more.

**Three anti-vacuity rules, each of which the I8088 conversion learned by
getting it wrong.** They are in this document rather than left implicit because
each one cost that epic a session.

- **No `is_modeled` flag.** Declaring an opcode unmodeled removes it from the
  denominator, so its wrong cases never appear as failures. A row that is hard
  must be a visible failure, not a smaller denominator.
- **No skip list without an expiry.** The I8088 found the same instruction
  hiding behind a skip list and an `is_modeled` flag simultaneously, 80,000
  vectors checked by nothing, with neither number moving when they were wrong.
  The 68000 state gate has no skip list today. It must not acquire one.
- **The gate needs a floor that ratchets.** A gate that reports a percentage and
  cannot fail is how a number that has not moved in several sessions stops
  reading as a problem.

And the reporting rule, which is the other thing that epic paid for: **report
every rate split by population, from the moment the comparison exists**, not once
the aggregate stops moving. For the I8088 the split that mattered was empty
queue against prefetched, and it was a fifteenfold gap hiding inside a single
number. The natural splits here are supervisor against user, memory-touching
against register-only, and word-aligned against odd.

## M1 as built, and what it measured

**Landed 2026-09-08.** The gate exists and no CPU code changed. Two rungs only:
`length`, and the transfer kinds in order. Rungs 3 to 6 compare *when* a cycle
runs, and an atomic core has no answer, so reporting them now would produce a
structural zero that reads like a timing result.

| population | cases | length | kinds | mean delta |
|---|---|---|---|---|
| **680x0**, all | 1,000,060 | **81.88%** | **58.38%** | +0.47 |
| ... touches memory | 612,693 | 72.92% | 33.01% | +0.31 |
| ... registers only | 387,367 | 96.06% | 98.50% | +0.73 |
| **m68000**, all | 317,500 | **77.75%** | **55.35%** | -1.14 |
| ... touches memory | 199,886 | 66.92% | 30.49% | -2.20 |
| ... registers only | 117,614 | 96.15% | 97.60% | +0.66 |

**The population split is the result, not the aggregate.** Register-only
instructions are already near-exact on both suites, 96% on length and 98% on
kinds, because there is no bus ordering to get wrong and the documented table is
right. Everything touching memory collapses to a third on kinds. The gap the
conversion has to close is entirely in the operand path, which is what M2 and M4
are, and the aggregates would have hidden that behind one number.

**The mean delta is small while the exact rate is not, which is the signature of
errors canceling.** +0.47 clocks on 680x0 against 81.88% exact: the misses run
in both directions and very nearly sum away. Any future report that quotes only
a mean here is quoting two mistakes agreeing to look like none.

**Two findings about the corpora, both from running them.**

- **The pinned `680x0` snapshot contains no user-mode vectors at all.** Zero of
  1,000,060 have the S bit clear, where its README implies about 1%. The
  classification is not the suspect: the same code splits `m68000` 158,841
  supervisor to 158,659 user. So privilege-dependent behavior is unexercised by
  that suite and covered roughly half the time by the other, which is a second
  concrete reason to keep both.
- **`STOP` found a latent harness bug on its first run.** `stopped` and `halted`
  are sticky and no register load clears them, so one case executing `STOP`
  parked the CPU for every case after it: 17 files of the `m68000` corpus, from
  `STOP.json.bin` onward, reported a clean 0.00% for a reason having nothing to
  do with timing. The gate now starts each case from a fresh CPU and asserts
  that no case hits the tick limit, because a case that never ran is not a case
  that disagreed. The `680x0` set has no `STOP` vectors, which is why its
  coverage had never exposed this.

**Where the two suites disagree**, 47 instructions by five points or more. The
largest are worth naming, and none is explained yet:

- `RESET`, `MOVEtoUSP` and `MOVEfromUSP` read 100% on kinds against `680x0` and
  about 50% against `m68000`. These are privileged, and `m68000` is half
  user-mode where `680x0` is none, so the obvious reading is that this is the
  coverage difference above rather than an oracle disagreement. **Unverified:**
  the test that would settle it is the per-file supervisor split, which the gate
  does not yet report.
- `RTE` and `MOVEtoCCR` read **0.00% on kinds against both suites**. That is not
  a disagreement between oracles, it is this core being wrong the same way
  twice, and `MOVE to CCR` is not even privileged.
- `MOVE.w` and `MOVE.l` sit near 17% on kinds on both.
- `CHK` and `MULU` are the worst length rows, 21% and 13% on `680x0`.

## M2 so far: the byte strobes, and what the contract cost

**Landed 2026-09-09.** The first half of M2. The four-clock bus cycle is still
ahead; this is the byte-strobe half, which closes np9x.1.

**The contract had to move first, and not the way Decision 4 assumed.**
`Bus16` with required methods collides with `BusMasterComponent`, which fixes
its own bus bound and is a supertrait of `Cpu`: the M68000 must implement it,
so its entry point received a `B: Bus` that could not be asked for byte
methods, and an impl cannot narrow a trait method's bound. Putting the byte
methods on `Bus` itself would have reached 166 impls, about 161 of them 8-bit
buses where a strobe means nothing. So the bus moved from a method parameter to
a **trait** parameter on `BusMasterComponent` and `Cpu`, which is where a bound
belongs if implementors are to differ. That landed as its own commit, with no
behavior change and 141 suites green.

It forced one further split, and the compiler found it rather than review:
`signal_interrupt` and `is_sleeping` never mention the bus, so on a
bus-parameterized trait they became uncallable with nothing to infer `B` from.
They are properties of the core alone and are now `CpuControl`.

**What the audit found.** Every byte-wide part on all four boards hangs off
D0-D7, so it answers at odd addresses only and a UDS transfer never selects it:
the NVRAM, ADC channel latch and three POKEYs on Food Fight; the two POKEYs and
NVRAM on Quantum; the EEPROM, bank select, sound latch and ADC on Atari System
1. The exception is the strobed registers, which fire on either half because
the access is the event rather than its data: the watchdogs, the VBLANK
acknowledge, the EEPROM unlock. Getting that distinction backwards was a real
mistake made and caught here: the first draft gated the strobes behind the
odd-address test too, which would have made a byte write to the watchdog do
nothing.

**The measurement.**

| rung | before | after |
|---|---|---|
| Transfer kinds, 680x0 | 58.38% | **67.24%** |
| ... touches memory | 33.01% | **47.48%** |
| Transfer kinds, m68000 | 55.35% | **64.03%** |
| ... touches memory | 30.49% | **44.28%** |
| Cycle count, both | 81.88% / 77.75% | **unchanged** |

**Cycle count not moving is the check, not a disappointment.** Removing a
phantom read changes the *sequence* of transfers, not what the documented table
charges, so a core whose timing still comes from that table should score
exactly the same on rung 1. It did, to the digit. Register-only cases did not
move either, having no byte operands.

**np9x.1's acceptance is pinned by six tests, and they were made to fail.**
Restoring the read-modify-write fails the three that pin the write path and
leaves the byte read, the preserved neighbor and the word write passing, which
is the discrimination wanted: the neighbor test passes under a read-modify-write
precisely because RAM hides the phantom read, and that is why it cannot be the
only check.

**The four boards are unmoved**: golden frames, boot, save-state and audio all
pass, so removing the phantom read changed no picture, no sound and no boot.

## M3 as built: the queue, and where the refill goes

**Landed 2026-09-09.** Two words in `core/src/cpu/m68000/prefetch.rs`, refilled
behind every consumed word and discarded by every control transfer.
`prefetch_pc` is gone, `pc` is private, and the hypothesis this milestone was
written on held: the whole memory-touching count gap was queue-shaped.

| rung | M2 | M3 |
|---|---|---|
| **680x0** length | 81.88% | **88.34%** |
| ... transfer kinds | 67.24% | **98.51%** |
| ... transfer count | 71.60% | **98.87%** |
| ... final PC and queue | - | **100.00%** |
| **m68000** length | 77.75% | **78.66%** |
| ... transfer kinds | 64.03% | **98.14%** |
| ... transfer count | 68.94% | **99.15%** |
| ... final PC and queue | - | **99.61%** |

**Where the refill goes was read off the traces, not assumed**, with
`m68000_trace_shapes` reducing every recorded case to its ordered bus activity
so the rule could be derived from 1.3 million cases rather than from a handful.
It has two halves. A word is normally consumed by refilling the hole first, so
`ADDI.b #, (d16, A7)` records two program reads before its operand read and a
third before its write. But **an instruction about to discard the queue does not
refill it**: a taken `Bcc` with a word displacement is ten clocks, which is two
transfers, and both of them are at the target. Refilling there would make it
three transfers and twelve clocks, so the branch family consumes without
refilling and the trailing refill lands at the finish.

Placement is then a per-family declaration: `MOVE` refills after its write,
except to `-(An)` where the decrement gives the prefetch a slot; the
read-modify-write families refill before theirs; `JSR` fetches one word at the
target, pushes, then fetches the second; `PEA` refills before its push; `STOP`
consumes without refilling at all and finishes without one.

**The two sites M2 left on the table became ordinary, which was the stated test
of whether this milestone worked.** Address-error entry is fifty clocks: eleven
transfers and six idle, and the two transfers that were missing are the refills
at the handler. `STOP` is four clocks and no bus cycle, because both its words
came out of the queue and the part stops before refilling.

**The residual is named rather than described.** The gate reports its own
misses by shape pair: `TAS`'s indivisible cycle (it records one transfer where
this core makes two), `MOVEM`'s trailing read, the long `ADDX`/`SUBX` refill
that sits *between* the two write words, and the rarer `PEA`/`MOVE` absolute
forms whose refills bunch one slot differently. All are M5's.

**Splitting the faulting cases out is what explained the length rung**, and it
also found a disagreement between the corpora worth recording: on cases ending
in an address error, `680x0` records six clocks of internal time and no cycle
for the aborted access while `m68000` records ten and the aborted cycle as well,
a difference of exactly eight clocks. This core matches `680x0` and the manual,
so it scores 56.74% there and 0.00% against the other set, at a mean of -8.91
clocks. On cases that complete, the two corpora agree with each other and with
this core: 95.19% and 95.36%.

**Two defects the queue exposed**, neither of them a timing question:

- `Scc` reads its destination before writing it. This core said the opposite in
  a comment and charged the missing transfer as time off the bus, so the total
  was right with the wrong activity underneath it, which is the exact failure
  `finish_from_bus` exists to prevent.
- `UNLK` moved A7 to An *before* the pop, so an odd An made the exception frame
  push itself fault and this core halted on a double bus fault where the part
  takes an ordinary address error. 530 cases of the microcode-derived corpus
  record the frame written on the stack the instruction started with. The
  documentation-derived corpus has no such case, which is why it read 100% on
  that instruction throughout.

**Road Runner's golden frame moved, and the mechanism is one line.** Not the
Slapstic: restoring the old snoop position leaves the new frame unchanged, and
so does re-reading each instruction word at consumption time instead of taking
it from the queue, so neither what that board's protection sees nor what the
CPU executes has changed. It is the **two fetches that fill an empty queue after
reset**. They cost the first instruction eight clocks it never used to pay,
which shifts the machine's phase against video timing once, at boot, and its
attract animation lands one step further along. Filling the queue inside `reset`,
where the clocks are charged to no instruction, restores the previous frame
byte for byte after 1800 frames, which is both how the mechanism was identified
and a model of a part that starts with a queue it never fetched. The
recapture is scoped to that machine; 38 of 39 frames are unchanged.

## M4 as built: the loader, the bus unit, and a body that runs twice

**Landed 2026-09-11.** Rungs 3, 4 and 5 are reported for the first time, and
rung 3 goes from the structural zero an atomic core has to give to 76.91% and
72.20%.

| rung | M3 | M4 |
|---|---|---|
| **680x0** length | 88.34% | **89.11%** |
| ... on cases that complete | 95.19% | **96.12%** |
| ... transfer kinds | 98.51% | **98.59%** |
| ... transfer kinds, on cases that fault | 99.97% | **99.9994%** |
| ... transfer count | 98.87% | 98.87% |
| ... **positions in clocks** | - | **76.91%** |
| ... positions, completed | - | **93.58%** |
| ... positions, >1 data transaction | - | **55.10%** |
| ... address, size and data | - | **79.98%** |
| ... function code | - | **98.14%** |
| **m68000** length | 78.66% | **79.40%** |
| ... transfer kinds | 98.14% | **98.23%** |
| ... positions in clocks | - | **72.20%** |
| ... positions, completed | - | **87.53%** |

Three things do the work, and only the third was in the plan's shape.

**The loader** takes the opcode before the body runs, burns the addressing
mode's arithmetic in front of it, issues the refill behind the opcode on a clock
of its own, and drives the trailing refills one per four clocks afterwards. It
needs **no staging buffer**, which is the discovery that made it small: taking a
word out of the queue fills the hole before it pops, so a body that finds the
queue full issues nothing and takes the word the loader fetched.

**The bus unit** takes a cycle nothing in the instruction waits on and runs it
later: a write, whose value is already decided, and a queue refill. `CLR.w (A4)`
is the case to read it by, recorded as three cycles on clocks 0, 4 and 8 and
issued from a body that runs on one.

**A body that suspends and runs again** is what reaches an operand *read*, which
cannot be handed over because the body is about to use what it returns. A cycle
the body has not run before, arriving on a clock that already has one, unwinds
the body: the registers go back, the clocks of the cycles it did run are spent,
and the body runs again with those cycles served from a log instead of the bus.
It reaches the next one having made no access twice and runs it on a clock of
its own.

### What the plan got wrong

**The loader's ceiling was lower than the milestone needed, and saying so in
advance is what made that visible.** The issue names `read_imm_word` as the seam
and the i8088's loader as the shape, and both were right as far as they went.
But the gate splits the corpus by data-transfer count, because a per-clock queue
in front of an atomic executor cannot put two data transfers on two clocks:
526,777 cases of 1,000,060 make at most one, so the aggregate ceiling for the
loader alone is about 52%. The loader reached 37.93%. Everything above that came
from the executor ceasing to be atomic, which the issue's own warning against a
generic operand pipeline reads as a thing to avoid.

**The mechanism is not per family, and the acceptance asked for one family per
commit.** What moved eleven points of rung 3 is four lines in two access
primitives and a state the loader already had a sibling of. The per-family work
was the *exceptions*: where internal time sits relative to a fetch, declared at
the call site the way M3 declared refill placement.

**The fold-in rows were not waiting for the pipeline.** `ADDA.l`, `SUBA.l` and
`SUBX.w` were folded into this milestone because their sub-clock mean deltas
said a subset of addressing modes was two clocks short and only a pipeline could
say which. They were fixed before the pipeline existed, by a by-addressing-mode
instrument and one mechanism: **a long ALU pass costs two more clocks when its
operand is not from memory.** The ALU is 16 bits, so a long operation is two
passes; with a memory operand the high pass shares a step with the prefetch,
without one it needs a step of its own. `CMP` is the control that makes this a
mechanism rather than a fitted number: same two passes, no result to place, two
clocks either way, and it stayed exact through the change.

**A table that states where internal time sits cannot be checked the way the
other two were.** `extension_words` and `suppresses_refill` are asserted against
what the executor actually did, on all 1,083,864 completed cases, before
anything uses them. `leading_internal` cannot be: the executor does not place
internal time anywhere, so there is nothing to compare against and any check
would measure the shape of this core's code. Rung 3 is its check. An attempt at
a direct one was written, run, rejected on 22,337 cases in 26 shapes, and thrown
away; it earned its keep first by finding two real errors in the table.

### The instrument, again

M1's lesson was that a population split is the result and the aggregate hides
it. M4's is the same lesson one level down: **a rate says how much is left and a
shape list says which instructions, and neither says how many different things
are wrong.** Rung 3's residual is now classified by the first clock that
disagrees, which separates a transfer bunched onto the clock of the one before
it (a body running two bus cycles in one tick, which needs suspension) from a
transfer on a clock of its own that is merely early (a placement question, which
does not). Both print as two lists of numbers that differ.

That classification is what made the milestone finishable rather than open
ended. Of 328,853 misses before the suspension work, 178,038 were cases that
fault, which sum to the address-error population and are exception entry, all of
it M5's. Of the 150,815 on cases that complete, **115,692 were one mechanism**.
After it they are 8,302, and every one of the 160 largest remaining shapes,
covering 161,056 of 216,555 misses, is exception entry or mul/div.

**Rung 2's report was hiding this milestone's last item, and the defect was in
the key.** A transfer-sequence mismatch was counted by the shape pair alone, so
one shape was one row however many instructions reached it, labelled with
whichever vector file had been read first. `MOVEM.l` sorts before `MOVE.w`:
every `MOVE` case sharing a shape with `MOVEM` was counted under `MOVEM`'s name
and the `MOVE` rows never appeared at all. What looked like 45 shapes was 62.
The rows also carried no example case, and a shape pair does not say which
encoding reached it: the same mnemonic runs different sequences for different
source modes, so reading a row without one invites fixing the wrong half, which
is what the first attempt at `MOVE` did. Both are the same lesson as M1's
population split and M4's own by-addressing-mode instrument, at a third place:
**an aggregate keyed on too little is not a measurement of the thing it
names.**

### Three corpus disagreements, all settled at the microcode

None fitted, and the rule that produced all three is **go to the die-extracted
microcode first, not to the corpora**.

- **`ADDQ.l`/`SUBQ.l` to `An`** read +2 on 731 cases of the
  documentation-derived corpus: uniform, large, one sided, and
  indistinguishable from a real defect. The part runs the identical sequence for
  the word and long encodings at eight clocks, and the microcode-derived corpus
  agrees with this core on every such case. Two clocks were nearly taken off a
  correct line.
- **A PC-relative operand is fetched from program space.** This one *lowered* a
  reported number, 98.51% to 98.06% on rung 5, because that corpus is what is
  wrong.
- **`LINK A7`** is two against two and stays as it is, because changing it fails
  1005 state vectors. The reason is in `stack.rs` and the residual is reported
  rather than hidden.

### Four defects no earlier rung could see

All four are invisible to the state gate and to rungs 1 and 2: same addresses,
same values, same count, same memory afterwards.

- The exception frame is written **PC low, SR, PC high**, at `sp-2`, `sp-6`,
  `sp-4`, with the stack pointer reaching its final value on the *second* write,
  so a frame that faults on its first leaves A7 untouched.
- A long read-modify-write result is written **low half first**: the part reads
  a long destination upwards and writes it back downwards, on a plain indirect,
  a displacement and a predecrement alike. Checked on three modes, because the
  first example found was a predecrement and that invites the wrong rule.
- The function code must be **latched when a cycle is handed over**, not read
  when it runs. A `BSR` that pushes in user mode and then faults would otherwise
  report its push at supervisor privilege, because the exception got there first.
- **A jump pays for address arithmetic every other instruction gets free.**
  `LEA (d16,An),An` adds the displacement in the same microcode step that puts
  the next fetch's address on the bus, so the add costs nothing; `JMP (d16,An)`
  cannot, because the address that add produces *is* the next fetch's address.

### What is left, and whose it is

Rung 3's residual is 216,555 cases on the documentation-derived corpus, and all
but about a quarter of it is in two M5 families:

- **Exception entry**, 178,038 cases, which is the whole faulting side. Its
  frame writes are driven together rather than one per four clocks, because
  entry reached from the state machine has no body to unwind and `flush_pending`
  puts them all on one clock. Making it resumable the way a body is, is the
  obvious move and is M5's.
- **mul/div**, whose data-dependent internal time is measured and named:
  +47.76 clocks mean on `DIVU`, +68.28 on `DIVS`.
- On cases that complete, 12,757 remain on a clock of their own but early,
  10,978 with the first transfer early, 8,302 with a read still bunched onto a
  read, and 5,702 with a write bunched onto a write. The read-on-read ones are
  the refills a body drives itself, which do not suspend: `refill_prefetch` is
  infallible and making it suspend means making `take_word` and `read_imm_word`
  fallible, across every call site.

`MOVEM` is capped rather than excluded: sixteen cycles of one body can be given
back to a later run of it, which covers every instruction but `MOVEM.l`, whose
long form moves up to thirty-two words. Past the limit it keeps running with its
remaining cycles on one clock, which is where all of them used to be.

**Rung 2 is finished for this milestone's families.** Its residual is 14,084
cases in 48 shapes, and what remains is `TAS`, the long `ADDX`/`SUBX` refill
that sits between the two write words, and `MOVEM`'s trailing read: the three
M3 named and M5 owns. `PEA` and `MOVE` were this milestone's and are exact:

- **`MOVE` to an absolute long destination, from a memory source**, reads the
  second address word, forms the address from it and the first, writes, and only
  then prefetches again. The shared decode took both words first, which is the
  right count in the wrong order. A register or immediate source does read both
  up front, which is the same condition the stacked-PC rule beside it already
  turns on rather than a second rule.
- **`PEA` refills before it pushes, except from an absolute address.** The other
  control modes have address arithmetic and the part slots the prefetch into a
  step it is already spending on it; an absolute address arrives ready to use in
  its extension words, so there is no such step before the push and the fetch
  falls through to the one at the end of the instruction. That is the jump's
  leading time seen from the other side.

Both are exact on every rung on both corpora now, and the faulting path's
transfer sequence with them: one case of 178,089 differs and it is a `MOVEM`.

### Exception entry is a body in its own right

The instruction that faulted is over, so there is nothing to unwind to, and
without a body of its own the entry drove all eleven of its cycles on one clock.
Four mechanisms, and the whole faulting side of rung 3 depends on them:

- entry gets its own state capture and replay log (`BodyKind`);
- a read **waits** for the outstanding list to drain rather than flushing it,
  wherever the body can be unwound;
- the bus unit's list carries steps that drive nothing (`PendingCycle::Idle`),
  because entry has a gap in the middle: its two fetches at the handler are six
  clocks apart, not four;
- cycles driven belong to the **clock**, not to whatever drove them.
  `tick_cycles` is zeroed at the top of `execute_cycle`. Interrupt entry never
  runs through a body, and zeroing that count inside one is what moved a golden
  frame.

Where the idle steps fall is per source and taken from the part: four in front
of the frame for `TRAP`, the illegal and privilege vectors, a zero divide and
`CHK`; six for an interrupt; none for `TRAPV`, whose fetch does the setup those
steps would; twelve for an address error.

**The group-0 frame is written in the part's order**, which is the short frame's
interleave twice: sp-2, sp-6, sp-4, sp-8, sp-10, sp-14, sp-12, with the
instruction register alone between the two halves. Rung 4 had read 0.00% on
every faulting case on both corpora until this was found, and it was this one
defect: the seven-word frame was being written downwards.

### The families, and what the part said about each

- **`MULU`/`MULS` and `DIVU`/`DIVS`** charged their worst case flat. Both are
  loops whose trip count depends on the data, transcribed one microcode step at
  a time: a multiply costs two clocks per one bit in its source, and a restoring
  divide costs six clocks a pass where the subtract takes and eight where the
  old remainder has to be put back. A divide fetches *after* its loop where a
  multiply fetches before, because the part's multiply issues the refill in the
  step that starts the loop and its divide has no such step.
- **`TAS` is one held bus cycle**, ten clocks of read, two clocks, write, and
  then the prefetch: fourteen in all, not a read and a separate write.
  `BusSignals` gained an `rmw` flag and the recording bus folds the write half
  into the announced cycle.
- **`MOVEM` loads read one word past the block** and throw it away, both sizes.
  The part's loop runs one read ahead of itself, so a list of n registers costs
  n + 1 reads and the last is never stored. It is a real access at a real
  address, which a device mapped just past the block can see.
- **A PC-relative `MOVEM` reads its whole list from program space**, not just
  the extension word that formed the address.
- **`MOVEP` and the three BCD instructions needed nothing.** They were read
  against the microcode and already exact: `MOVEP.w`, `MOVEP.l`, `ABCD`, `SBCD`
  and `NBCD` each read 100.00% on all six rungs on both corpora. Reading the
  part first is what turned two of M5's six families into a null result instead
  of a change; the reverse order would have produced edits in search of a
  number.

### A load that resumes, because a load cannot be replayed

`MOVEM.l` moves up to thirty-two words and the replay log holds sixteen, so past
the sixteenth the body could not suspend and the rest of the list ran on one
clock. **A cursor alone cannot fix that**: the unwind restores the register
file, so skipping the registers already transferred would lose their values.

So the load **commits**. Once a register is loaded, `commit_body_state`
re-captures the body state and empties the log, and `MovemLoad` (outside
`BodyState`, because the unwind must not restore it) says which register to
re-enter at. The log then never holds more than one register's worth of cycles
and every transfer can suspend however long the list is.

Raising the cap was the alternative and was rejected twice over: the log is
walked from the top on every attempt, so a thirty-two word load would cost a
quadratic number of replay steps on the core whose throughput binds this
conversion, and sixteen would still be a limit where the part has none.
`MOVEM.w` does not move and should not, at sixteen transfers for sixteen
registers; a change that had moved the word form too would have been changing
something other than the cap.

### Six corpus disagreements, all resolved at the microcode

Each has its reason where the code is, and none of them is a fitted constant:

1. **The aborted access costs its bus cycle and four clocks more**
   (`ABORTED_ACCESS_CLOCKS`). Nothing reaches the bus, since the address strobe
   is never asserted. The manual's fifty is for entry alone and says nothing
   about the attempt. One constant with a mechanism is a disagreement; the four
   buckets it replaced were a defect.
2. **`CHK` does not refill in front of its trap**, and it decides in two steps:
   the first traps on the sign *or the overflow* of bound minus value, the
   second, two clocks later, on the value's own sign (`op_chk`). The other
   corpus records the refill and compensates with four clocks less internal
   time, so `CHK`'s total is right there and its bus activity is not, which is
   the two-errors-cancelling shape this ladder exists to catch.
3. **`TAS` is one indivisible cycle** (`read_modify_write_byte`).
4. **`DIVS` has a late overflow band** the documentation-derived corpus does not
   model: where the quotient's magnitude lands between 32768 and 65535 the part
   cannot tell before the loop, so it runs all sixteen passes and reports the
   overflow in its tail (`divs_internal`).
5. **`RTE` and `RTR` pop straight upwards** (`pop_status_and_pc`).
6. **A PC-relative operand is read from program space**, extended this milestone
   to `MOVEM`'s list. The documentation-derived corpus records the data code on
   4,658 cases in 36 shapes, every one of them `recorded fc5 ours fc6`.

A mistake worth keeping on the record: `RTE` and `RTR` were changed to pop the
high half first, from a dump of the documentation-derived corpus rather than
from the part, and reverted when the microcode was read. That corpus was wrong,
and the rule this project states most emphatically is the one that would have
caught it before the edit rather than after.

### The instrument, again

- **A clock-delta histogram per population**, commonest first. It said 0, -2,

  `ASL`, `MOVEfromSR`, `ADDX`, `SUBX` and `JSR` with a displacement, 0 was

- **Rung-3 rows name a case.** A pair of clock lists says two sequences differ;
  it does not say which encoding produced them, and one instruction name covers
  twelve addressing modes whose microcode is twelve different sequences.

### Throughput

Measured on the original host, the one the M1 baseline and the 2x floor were
argued on, established by measuring the M4 commit here in a worktree rather than
trusting the recorded figure: the delta being looked for is about 2.5%, which is
the same size as the gap between the two hosts. Two runs of each, agreeing
within 1%, fastest rep of five, 600 frames, 1800 warmup.

| machine | M1 emul ms/f | M4 emul ms/f | M5 emul ms/f | M4 to M5 | M1 to M5 | real time |
|---|---|---|---|---|---|---|
| foodf | 1.594 | 2.139 | 2.198 | +2.8% | +37.9% | 7.46x |
| quantum | 1.862 | 2.427 | 2.536 | +4.5% | +36.2% | 3.91x |
| marble | 3.026 | 3.882 | 3.957 | +1.9% | +30.8% | 4.21x |
| roadrunner | 3.310 | 4.007 | 4.106 | **+2.5%** | **+24.0%** | **4.06x** |

Road Runner binds at **4.06x** against the 2x floor, so M6 and M7 have 2.03x of
headroom. This milestone added a suspending exception-entry body, a longer
pending list, per-operand multiply and divide loops and a resuming `MOVEM`, for
2.5% of the binding machine's emulation time; the whole conversion has now spent
about a quarter of a budget that was allowed to grow by 152%.

**The `capture_body_state` skip was measured and not built.** The plan was to
skip the body-state capture for bodies that cannot suspend. Its ceiling was
measured first, by making the capture cost *twice* as much rather than by
skipping it unsoundly, which keeps the program correct and so measures the same
program: one capture is worth 2.8% of foodf's emulation time and 1.2% of Road
Runner's. So the whole optimization can return at most 1.2% on the machine that
binds, and only for the fraction of instructions that cannot suspend. Collecting
it needs a per-encoding predicate for "makes at most one operand read", whose
hard cases are the `-(An),-(An)` forms of `ADDX`, `SUBX`, `CMPM`, `ABCD` and
`SBCD`, encoded with the same EA-mode field their register forms use. That is
the artifact M4 wrote, checked, rejected on 22,337 cases and threw away. Not
worth its risk at 1.2%, and the number is recorded here so it is not re-derived.

### What is left, and whose it is

Rung 3's residual on the microcode-derived corpus is 5,329 cases in 264 shapes,
and it is three mechanisms:

- **2,231 cases are a body-driven refill that cannot suspend**, so two program
  reads land on one clock. `refill_prefetch` is infallible, and making it
  suspend means making `take_word`, `read_imm_word` and `fill_prefetch` fallible
  across every call site. It also blocks placing internal time that sits between
  two fetches, which is why an indexed `MOVEM`'s two-clock index add is still at
  the end of the instruction rather than in the middle, on 588 cases:
  `defer_idle`'s entry is discarded by the `flush_pending` the next refill
  performs. `phosphor-emulator-d31l`.
- **2,437 cases have every transfer on a clock of its own but two clocks early**,
  and 661 more have the first transfer early or late. It is a two-clock shift in
  one direction or the other: `MOVEtoSR` two late, the bit operations and
  `MOVE.b` two early. `phosphor-emulator-4sdm` owns the bit-operation half, and
  `MOVEM`'s 588 indexed cases sit in this class rather than beside it.

Rung 2's residual is `TAS` on the corpus whose README disqualifies it for `TAS`,
and **834 cases of `ADDX.l`/`SUBX.l`**, which put their refill between their two
write words where this core puts it in front of both:
`phosphor-emulator-7wmg`.

Rung 4's residual on that corpus is 40,323 cases and it is a convention, not a
defect: its `pc` is the generator's next-prefetch address, so a PC an
instruction writes into memory differs from ours by the prefetch lead. The gate
reconciles that for the initial and final states and cannot for a value in
memory. That is why the faulting population reads 28.07% there while reading
95.46% on the other corpus, and it is floored where it stands.

## Decision 4: byte strobes are not a separate project

`phosphor-emulator-contained-fidelity-np9x.1` says a 68000 byte write should be
one half-word transaction rather than a word read-modify-write.
`addressing.rs:238` does the RMW today and says so, and its own comment already
concedes the point: "The real 68010 performs a byte write as a single bus cycle
... The word read below is an emulation artifact".

**The per-cycle gate cannot pass while that is in place.** A byte write appears
in the oracle as one transaction of size `.b` at the unaligned address with the
strobe implied by address bit 0. Ours would replay as a word read plus a word
write, so rungs 2, 4 and 5 fail on every byte write in the corpus. The bug and
the conversion are the same change, so np9x.1 is folded into M2 rather than
sequenced against it.

**Contract shape.** A new extension trait in `core/src/core/bus.rs`:

```rust
pub trait Bus16: Bus<Address = u32, Data = u16> {
    fn read_byte(&mut self, master: BusMaster, addr: u32) -> u8;
    fn write_byte(&mut self, master: BusMaster, addr: u32, data: u8);
}
```

The 68000 bounds on `B: Bus16 + ?Sized`, and the four boards plus the three test
buses (`SimpleSystem68k`, `TestBus68k`, `TracingBus68k`) implement it. The
methods are **required, not provided**: a default implementation would be
today's RMW, and a board that forgot to override it would inherit the bug
silently, which is precisely the failure mode np9x.1 describes. A shared
`rmw_byte` helper stays available for genuinely RAM-backed buses, but a bus opts
into it by calling it.

The blast radius is small because
[`concrete-bus-dispatch.md`](concrete-bus-dispatch.md) already landed: every
machine dispatches at a concrete bus type with no `dyn` on the CPU-to-bus path,
so an extra trait bound monomorphizes and costs nothing at runtime.

np9x.1's own acceptance criterion stands unchanged and is the check that this
half is right: **a write-only device register on a 68000 board sees exactly one
access for a byte write, and no read.** It needs a test that would fail today.
The audit it calls for, over the four boards, for registers currently absorbing
a phantom read, is part of M2 and is the risk in it.

## Decision 5: interaction with concrete bus dispatch

None left. That work is done: `bus_split!` is deleted, every machine dispatches
at a concrete bus, and there is no `unsafe` on any CPU-to-bus path. The issue
lists it as an open interaction because it was open when the issue was written.

The conversion inherits two things from it. The trait bound above is free, as
above. And the reason it was done at all, that every read and write in a running
machine used to be an indirect call the optimizer could not see through, is why
a per-cycle core is affordable here at all: a per-clock tick makes many more,
much smaller calls, and they now inline.

## Decision 6: the 68010 gets a datasheet delta, and a label saying so

Marble Madness and Road Runner run Atari System 1, whose main CPU is a 68010
(`atari_system1.rs:616`). Food Fight and Quantum are 68000s. So half the shipped
68000-class boards are on a variant for which **no bus-trace oracle exists**.
This was checked rather than assumed:

- **Neither vector set covers it, and no third one exists.** `680x0` ships
  `68000/v1` only and describes itself as tests "for the 68000"; `m68000` is
  68000 by name and by description. The publishing organization has 22
  repositories, covering the 6502 family, the 65816, the Z80, the SM83, the
  SPC700, the 8086/8088/80186/80286/80386, the V20, the R3000, the SH4, the
  HuC6280, the ARM7TDMI and the TLCS900H. **Not one of them is a 68010, a 68020,
  or any other 680x0 family member.** So this is an absence in the field, not a
  gap in our checkout.
- **The 68010 did not move when the 68000 did.** The microcode-level core became
  the mainline 68000 implementation in that tree in 2023, which is what makes
  the `m68000` vector set worth having. The 68010 stayed behind: `m68010.h`
  still reads `class m68010_device : public m68000_musashi_device`, which is
  instruction-level with cycle totals and no bus sequence.
- The microcode-level implementation instantiates the 68000, 68008 and MCU
  variants. There is no 68010 built from it, which also means the stronger of
  the two vector sets could not simply be extended to cover one.
- **`m68k-rs` has no generator.** It supports the 68010 as a CPU model, but it
  only consumes fixtures, and the fixtures it consumes are the SingleStepTests
  sets plus Musashi binaries. Its own 68010 behavior has never been checked
  against anything, because there is nothing to check it against.

**The decision is to do it anyway, from the datasheet, behind the variant gate,
and to label it.** The 68000 conversion is validated against a sequence oracle;
the 68010 delta is not, and the README must say which is which rather than
letting "cycle-accurate 68000 family" cover both.

### Generated 68010 vectors, as a differential net and not as an oracle

68010 vectors can be generated, by driving `m68k-rs` or Musashi over randomized
states and recording what they do. **Do it, and be exact about what it is for.**

**It is not an oracle, and treating it as one would be the worst mistake
available here.** Musashi charges a cycle total looked up from a table, so a
generated trace's intra-instruction placement would be an artifact of its
interpreter, and its totals are a reading of the same tables we would be reading
ourselves. `m68k-rs` models 68010 access ordering, but its own sequence and
per-access timing checks are ignored rather than gating, and its 68010 has never
been validated by anything. Either way, running our ladder against such a set
would produce a number that cannot falsify its generator: subject and standard
from the same place, which is the shape this project keeps writing down.

**What it is for is the question it can actually answer: where do two
independent readings of the 68010 diverge?** That is a real signal. A divergence
is a prompt to go back to the manual and to the microcode, never a value to
adopt. Concretely:

- Report the divergence set, per instruction and per addressing mode, the way
  the per-row residual instrument does for the 68000.
- A row where we and the generator agree is weak evidence and is recorded as
  weak.
- A row where we diverge is a finding to resolve from the datasheet, and the
  resolution is written down with its source.
- **No constant in this core is ever set to make a generated row agree.**

The checks that can actually fail stay the three below, and the conformance-ROM
loop count remains the only one anywhere near hardware.

What the delta pass covers, as an inventory rather than a list of answers:

- **Not-taken branch timing.** `phosphor-emulator-zi4z` already measured this and
  is absorbed here: `branch.rs` charges the 68000's 8 clocks for a not-taken
  `Bcc.b` unconditionally, where the 68010 takes 6. That issue's measurement,
  1562 poll-loop iterations against a reference's 1608 across 240 active
  scanlines on Road Runner, is the independent check for this one row and both
  sides landed within one iteration of their own arithmetic.
- **DBcc loop mode**, which is the structurally interesting one and the reason
  zi4z explicitly declined to patch the branch row in isolation: a two-word loop
  runs out of the queue with no fetches at all on a 68010. That is a mechanism,
  not a constant, and it changes the bus sequence rather than only the total.
- **The remaining per-instruction timing differences**, which are a whole table
  and not five constants. Enumerated deltas visible in a reference's constants
  (not-taken `Bcc.w`, `DBcc` false with and without expiry, `Scc` register-true,
  `RESET` 132 against 130) sit *on top of* a separate per-instruction table, so
  the scope is a table pass.
- **The instructions the core currently decodes as bounded NOPs**: `MOVEC`,
  `MOVES`, `RTD`, and `MOVE from CCR`. None is exercised by a supervisor-mode
  game that leaves VBR at 0, and that is why they were deferred; a per-cycle
  claim for the variant should either implement them or restate the deferral.
- **The format $8 group-0 frame**, still unmodeled.

**The primary source is the family user's manual already cited in the core
README**, whose scope includes the 68010 and which carries its instruction
timing separately from the 68000's. Confirm that before scoping the pass; if it
does not, the pass needs a source before it needs an implementation.

**The check that must exist, because rule 3 applies hardest where there is no
oracle.** Reading our datasheet interpretation against another emulator's
datasheet interpretation is close to a check that cannot fail. What can fail:

1. The 68000 vectors still pass, unchanged, with `variant` at `M68000`. The
   delta must be gated, and a leak into the 68000 path shows up immediately.
2. The conformance-ROM loop measurement zi4z used, re-run on Road Runner, which
   is a whole-loop count on a real image rather than a table comparison.
3. Per-instruction tests asserting the *sequence* from the manual, not the
   total, for every row the pass changes.

## Decision 7: migration order

The state gate must be green at every commit rather than at the end, and the
ROM-gated suites must be run at every milestone that touches the bus.

The I8088's correction applies directly here and saves a false start: **the
first move is not a generic operand pipeline.** What that conversion actually
needed first was a loader, a state machine that walks the instruction's words and
hands them to an unchanged executor, because the executor's word-at-a-time
interface was already the right seam. The 68000's equivalent seam is
`read_imm_word`, which every instruction already funnels its extension words
through, and the EA layer's `Ea` resolution behind it.

The order is therefore:

1. **The gate, before any conversion** (M1). Deserialize `transactions`, replay
   against today's atomic core, report rungs 1 and 2 split by population. No CPU
   change at all. This is the number the decision gets made on.
2. **The bus contract and the four-clock bus cycle** (M2). `Bus16` and byte
   strobes, and every transaction takes four clocks instead of landing on one.
   Execution stays atomic behind it. Expect the count to get *worse* in places:
   this charges real time for accesses that were free, without yet crediting the
   queue for the fetches it saves.
3. **The prefetch queue** (M3). Two words, refill, flush on transfer. Expect the
   count to move sharply again, and in both directions, for the reason M2 of the
   I8088 conversion records: removing a wrong cost exposes a missing one, and two
   errors canceling is the failure mode the ladder exists to catch.
4. **The operand pipeline** (M4). Accesses move out of the instruction bodies
   into a shared per-clock pipeline, and the instruction bodies become pure
   compute over resolved operands. This is the bulk, and it is mostly mechanical
   because the `Ea` decode is already shared.
5. **The awkward set** (M5), one family per commit: `MOVEM`, `MULU`/`MULS`,
   `DIVU`/`DIVS`, `MOVEP`, the BCD instructions, `TAS` with its indivisible
   read-modify-write cycle, and the whole of exception entry including the
   address-error abort, which this core already models exactly at state level and
   must keep doing.
6. **The 68010 delta** (M6), as above.
7. **Board integration** (M7). Golden frames, audio, bench against the M1
   baseline, README status lines on both the core and the machines.

## Performance

Converting an atomic core to per-cycle costs throughput by construction, so the
baseline was taken before any work started, on the four boards that would carry
the change. Release build, 600 measured frames, 1800 warmup, 5 reps, fastest rep
reported:

```text
cargo run --release -p phosphor-bench -- --roms ~/ws/mame-runtime/roms \
  --machine foodf --machine quantum --machine marble --machine roadrunner \
  --frames 600 --warmup 1800 --reps 5
```

| machine | emul ms/f | render | audio | total ms/f | fps | realtime | spread |
|---|---|---|---|---|---|---|---|
| foodf | 1.594 | 0.005 | 0.000 | 1.599 | 625.5 | **10.29x** | 3.6% |
| quantum | 1.862 | 1.664 | 0.000 | 3.526 | 283.6 | **4.73x** | 2.0% |
| marble | 3.026 | 0.007 | 0.000 | 3.034 | 329.6 | **5.50x** | 3.3% |
| roadrunner | 3.310 | 0.007 | 0.000 | 3.318 | 301.4 | **5.03x** | 1.2% |

**Quantum is not the tight board.** It looks slowest at 4.73x, but 1.664 of its
3.526 ms per frame is the vector renderer, which this conversion does not touch.

**The bar, stated before the work rather than after it.** A per-cycle 68000 that
runs every one of these boards **comfortably above real time, with a floor of
2x**, is a success even if it is several times slower than today's core. Saying
so up front is what stops the benchmark being used to argue down a correctness
fix afterwards. Against that floor, and holding render and audio fixed, the
emulation cost may grow by:

| machine | emul now | emul budget at 2x | headroom |
|---|---|---|---|
| foodf | 1.594 | 8.21 | 5.15x |
| quantum | 1.862 | 6.68 | 3.59x |
| marble | 3.026 | 8.32 | 2.75x |
| roadrunner | 3.310 | 8.33 | 2.52x |

**Road Runner binds, at 2.52x.** That is the number to hold the conversion
against, and it is tighter than it looks, which brings up the prediction this
document most wants on the record:

**The I8088's throughput increase will not repeat here.** That conversion ended
*faster* than it started, 5.87x against 5.59x, and the reason was specific: its
`ExecState::Execute(_)` was never constructed, so it retired a whole instruction
per call and ran roughly an order of magnitude more instructions per emulated
frame than the part does. Doing the right amount of work paid for running the
bus every T-state. **This core does not have that defect.** It burns its
documented cycles through 115 `finish()` sites and already executes about the
right number of instructions per frame, so there is no overcount to reclaim.
Every clock of bus modeling added here is added cost.

That prediction is checkable at M2, and if it turns out wrong it will be wrong
because this core is doing some other kind of work the hardware never did, which
is worth knowing on its own.

## Risks

- **Road Runner's 2.52x headroom.** The tightest constraint in the design and
  the reason M1 exists as a measure-only milestone. If M2 and M3 together spend
  more than about half of it, the decision to continue should be re-taken rather
  than assumed.
- **The Slapstic depends on fetch order today.** `prefetch_pc` is a shipped,
  load-bearing partial prefetch model with exactly one user. Replacing it with a
  real queue is a change to what that board's address-snooping hardware sees.
  The golden frame is the check and a moved frame needs a named mechanism, not a
  recapture.
- **The byte-strobe audit reaches four boards.** Removing the phantom read is
  correct, but any board register that has been absorbing it may have been
  written against the phantom. That is the whole content of np9x.1's "audit the
  four boards" and it is where M2's risk is, not in the trait.
- **The 68010 has no oracle.** Half the boards. Mitigated by the variant gate,
  the three checks in Decision 6, and by labeling; not eliminated.
- **Neither vector set is a hardware recording.** Both are implementation
  traces. A disagreement is evidence, not a verdict, and where one survives
  investigation it goes upstream. Running both is the mitigation.
- **The second set's format is explicitly not final.** Its README says so: "These
  may not be the final form; I may add new features, or adjust so that certain
  things go better". Pin the submodule at a commit and move it deliberately. A
  floating vector corpus would make a gate's number change without any change to
  this core, which is the one thing a regression net must never do.
- **Generated 68010 vectors are a standing temptation to fit.** The divergence
  report exists to point at rows worth re-reading the manual for. The moment a
  constant in this core is set to make a generated row agree, the whole 68010
  pass becomes a check that cannot fail, and it will read as progress.
- **The second set has named defects and they overlap the awkward set.** Its own
  README excludes `TAS` and `TRAPV` from "verified as good", and says the `TAS`
  timing specifically does not handle the 5-cycle read-modify-write. `TAS` is in
  M5. So for that one instruction the stronger-provenance set is the weaker
  authority, and the `680x0` set's `t` transaction kind is what to compare
  against. Read the caveats before trusting a residual, not after.
- **`MOVEM` and the divides are where the sequence risk concentrates**, as the
  equivalents did on the I8088, because their bus cycles are generated by a loop
  whose trip count depends on the data.

## Milestones

Each is an issue under the epic; each ends with the full state gate green and,
from M2 on, with the ROM-gated suites run.

- **M1. The gate, before any conversion.** Deserialize `transactions` and
  `length`, ingest the second vector set (the `.json.bin` decoder, the `m_au`
  PC reconciliation, and strobe normalization of bus-positioned byte data),
  replay against today's atomic core, and report rungs 1 and 2 against each set
  plus the set-against-set disagreement figure, all split by population. No CPU
  change. The submodule is already in the tree at
  `cpu-validation/test_data/m68000`. Deliverable is the harness plus the
  numbers, and they are what the "then decide" is decided on.
- **M2. Bus contract and the four-clock bus cycle.** `Bus16` with required byte
  methods, byte writes as one strobed transaction (closes np9x.1), the four-board
  audit, and every transaction occupying four clocks. Widen the gate to rung 3.
- **M3. The prefetch queue.** Two words, refill, explicit flush on every control
  transfer, `prefetch_pc` deleted. Widen to rung 6.
- **M4. The operand pipeline.** Per-clock operand accesses; instruction bodies
  become pure compute. Widen to rungs 4 and 5.
- **M5. The awkward set and exceptions.** `MOVEM`, mul/div, `MOVEP`, BCD, `TAS`,
  exception entry and the address-error abort, one family per commit. Landed:
  see [M5 as built](#m5-as-built-the-awkward-instructions-and-exception-entry-as-a-body).
- **M6. The 68010 delta.** Absorbs `phosphor-emulator-zi4z`. Datasheet-derived,
  variant-gated, labeled in the README as not oracle-backed. Includes generating
  68010 vectors and running them as a divergence report, never as a gate.
- **M7. Board integration.** Golden frames and audio on all four boards, bench
  against the M1 baseline, README status lines updated on the core and on the
  machines.

## Recommendation

**Do it, and re-take the decision after M2.**

For:

- The oracle exists, one of the two sets is already on disk, and it is a
  complete per-clock timeline rather than a summary. That was the one thing the
  issue said was missing and the one thing that would have made this the wrong
  core to convert.
- **There are two of them, independently generated**, one from the
  documentation and one from the part's die-extracted microcode. That is a
  better validation position than the I8088 conversion had in one respect: its
  hardware recording was stronger, but it was single-sourced, so a
  disagreement had nowhere to be adjudicated except by argument.
- Four boards rather than one, and three of them run the CPU clock at the pixel
  clock, so bus phase is video phase.
- One of the four already needed a hand-rolled partial prefetch model to work at
  all, which is the "can I point at the part?" test passing: the mechanism is
  missing, something is standing in for it, and the stand-in is in the tree.
- np9x.1 is a real latent bug on four shipped boards and this is the work that
  fixes it, rather than a second pass over the same interface.

Against, and both are real:

- Road Runner has 2.52x of headroom and this conversion, unlike the I8088's, has
  no overcount to reclaim.
- Half the boards are a variant with no oracle, so half the fleet gets a weaker
  claim than the other half no matter how well the 68000 half goes.

M1 costs little, changes no CPU code, and produces the number both objections
turn on. M2 produces the first real throughput measurement. Deciding again there,
against measurements rather than against this document, is what keeps the
option open that structurally right turns out measurably worse. If it does,
that has to be said out loud and labeled in the commit and in the source,
rather than shipped quietly.

## Verification

- The 1,000,058-vector state gate stays green throughout, with no skip list and
  no `is_modeled` flag.
- The per-cycle gate reports, per milestone, how many vectors match at the
  current rung, split by population and reported against each vector set
  separately, so progress is a number rather than an impression. It acquires a
  ratcheting floor once the rows are done.
- The set-against-set disagreement figure is reported alongside, and every case
  in it is either resolved against the microcode or carried as a named open
  question. A residual there is never grounds to change a constant in this core.
- np9x.1's acceptance holds: a write-only register on a 68000 board sees exactly
  one access for a byte write and no read, proved by a test that fails before
  M2.
- Golden frames and audio-sanity entries on foodf, quantum, marble and
  roadrunner are unchanged, or changed with a named mechanism and an image that
  was looked at.
- `phosphor-bench` on all four boards at each milestone, against the M1 baseline
  above, with the 2x floor as the stated bar. **A comparison names its host, and
  a delta is only quoted between two figures measured on the same one.** The
  tree moved machines during M4 and the two disagree by a uniform factor of
  about 1.8, so a milestone benched on one host and read against a baseline from
  the other would report a conversion that costs nothing, or one that costs
  twice what it does. The 2x floor itself is absolute and survives the move.
  **Measure the previous milestone's commit on the host in hand rather than
  quoting its recorded figure**, in a worktree, back to back with the new one.
  From M5: the delta being looked for was 2.5% and the gap between the two hosts
  was the same size, so the recorded number could not have told the two apart
  even though it happened to agree.
- **Measure an optimization's ceiling before building it.** The way to do that
  without measuring a different program is to make the suspect work cost twice
  as much rather than to remove it unsoundly. M5's `capture_body_state` skip was
  measured that way, came out at 1.2% on the binding machine, and was not built.
